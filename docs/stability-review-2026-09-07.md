# MioProxy 稳定性检查与修复记录

检查对象：本地 v1.0.3，起始提交 `73d26c5`，起始工作区干净。
本次检查重点是前端异步状态、连接轮询和发布检查；同时运行 Rust 库回归测试。
这不是全项目逐行审计，也不代表已完成原生 Windows 产品验收。

## 1. 发布检查可能误报成功（优先级高）

位置：`.github/workflows/release.yml`、`release-candidate.yml`、`release-readiness.yml`。

原来的源码验证步骤在同一个 PowerShell 脚本里依次执行 npm、cargo 和 git，
没有逐条检查外部进程退出码。前面的测试失败，后面的成功命令可能覆盖退出码，
使不满足质量要求的版本继续进入打包步骤。

修复：显式声明 `shell: pwsh`，每条命令后立即执行：

```powershell
if ($LASTEXITCODE -ne 0) { exit $LASTEXITCODE }
```

学习要点：PowerShell 脚本错误与外部程序失败不是同一回事。
对 npm、cargo 等程序，要在下一条命令覆盖退出码之前检查它。

验证：新测试从真实 YAML 提取源码验证脚本，用无副作用的命令替身模拟失败。
修复前，第一条命令失败后仍执行了全部 9 条命令并返回 0；
修复后，三条流水线的每一个失败位置都立即返回 17，全部成功时返回 0。
测试已接入 `npm run test:release-manifest`。
这里只验证了本地脚本行为，没有运行远端 GitHub Actions 或发布版本。

## 2. 停止内核后，旧连接请求仍能写回列表（优先级中）

位置：`src/hooks/useConnections.ts`。

复现顺序：请求 A 发出 → 内核停止并清空列表 → 请求 A 返回 → 旧列表又出现。
旧请求报错也会污染停止后的状态。快速重启时，旧请求的忙碌锁还会阻止新请求。

修复：为每轮启用周期记录 generation（代次）。请求开始时记住代次；
成功、失败以及 finally 释放锁时，都检查请求是否仍属于当前周期。
停止或卸载时让旧代次失效，并允许新的周期发出请求。
旧请求仍可能在底层完成，但已经无权修改当前界面状态。

学习要点：`clearInterval` 只阻止未来的轮询，不会取消已经发出的 Promise。
防止并发的布尔锁也不能单独判断结果是否过期。
尤其要检查 finally：旧请求不能释放新请求持有的锁。

验证：`src/hooks/useConnections.test.tsx` 覆盖停止后的迟到成功/失败、
旧请求未完成时重启、卸载后的响应以及旧请求不能释放新锁。
最初四个复现测试在修复前全部失败；修复后五个场景全部通过。

## 3. 系统代理旧请求报错会污染新的正常状态（优先级中）

位置：`src/App.tsx` 的 `refreshSystemProxy`。

原代码在成功分支检查请求序号，但 catch 分支没有检查。
因此，新请求已经确认开启成功后，旧请求的失败仍会设置错误状态并显示过期错误。

修复：成功和失败分支都检查组件仍挂载、请求序号仍是最新。
保持后端状态为权威来源，不改 Windows 代理所有权或实际开关行为。

学习要点：过期请求的错误也是过期数据；不要只保护成功结果。
新增回归测试先完成开启操作，再拒绝旧请求，确认不会出现过期错误。
该测试在修复前失败、修复后通过。
